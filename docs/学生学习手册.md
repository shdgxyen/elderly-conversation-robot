# 老人陪伴对话机器人 · 项目教学讲义

---

## 引言：项目概述

本项目要构建一个面向老人的桌面陪伴机器人。它具备以下能力：与老人语音聊天；在圆形屏幕上显示表情和状态；识别使用者身份；在获得授权的前提下保存对话内容；从长期对话中整理老人的经历，逐步生成老人的个人自传。

### 系统架构

系统由两台各司其职的计算机组成：

```text
┌─────────────────────────────┐
│ 机器人头部：ESP32-S3 开发板    │  职责：显示表情、采集声音、播放语音、
│ （esp32-firmware/，C 语言）   │       读取按键与隐私开关
└──────────────┬──────────────┘
               │ USB 串口连接，传输 JSON Lines 消息
┌──────────────▼──────────────┐
│ 底座：Raspberry Pi 5          │  职责：语音识别（STT）、对话生成（LLM）、
│ （pi-backend/，Python）       │       语音合成（TTS）、数据存储、人脸识别
└─────────────────────────────┘
```

一次完整的语音对话流程：老人说话 → 头部麦克风采集 → 音频传给底座 → STT 将语音转为文字 → LLM 生成回复 → TTS 将文字转为语音 → 音频传回头部 → 喇叭播放，同时屏幕显示说话表情。

### 设计原则

第一，**分工原则**：树莓派负责"听懂、思考、识别、存储、生成"，ESP32 负责"显示、采集、播放、交互、状态反馈"。分析任何问题时，先判断它属于哪一端。

第二，**原型开发**：项目当前阶段使用模拟组件（Mock）代替尚未接入的真实硬件和云端服务，先验证整体流程，再逐个替换为真实实现。

第三，**隐私保护**：默认不保存原始音频和视频；摄像头仅用于人脸识别；麦克风和摄像头都有物理开关；老人表示"不要记录"的内容不进入长期记忆。这些规则贯穿所有章节。

## 第一章 项目认知与环境搭建

### 学习目标

理解系统的两端分工；在开发电脑上启动后端服务，完成第一次文本对话。

### 核心概念

**分工**。ESP32 与树莓派通过一根 USB 线通信，各自承担不同职责（见引言分工原则）。判断故障来源的第一步，就是确定问题发生在哪一端。

**原型与 Mock**。当前系统中的大模型、语音识别、语音合成均为模拟实现。模拟实现与真实实现接口一致，因此后续替换时其余代码不需要改动。

**终端（命令行）**。通过文字命令操作计算机的界面，是软件开发的基本工具。本章用到三个命令：`cd`（进入目录）、`ls`（列出内容）、`curl`（向服务发送 HTTP 请求）。

### 实践步骤

1. 打开终端，进入项目目录，浏览目录结构，对照引言中的架构图辨认 `pi-backend/`、`esp32-firmware/`、`docs/`、`tools/` 四个目录的作用。
2. 依次执行：

   ```bash
   make setup
   cp pi-backend/.env.example pi-backend/.env
   make run
   ```

3. 浏览器访问 `http://127.0.0.1:8000/docs`，这是后端自动生成的 API 文档页面。
4. 另开一个终端，发送第一条对话请求：

   ```bash
   curl -X POST http://127.0.0.1:8000/chat/text \
     -H 'Content-Type: application/json' \
     -d '{"user_id":"user_001","text":"你好"}'
   ```

### 例题

**例 1.1** 老人对机器人说"我年轻时在纺织厂上班"。请按顺序写出这句话在系统中经过的五个处理环节，并标明每个环节发生在哪一端。

**解**：① 麦克风采集声音（ESP32）；② STT 将语音转为文字（树莓派）；③ LLM 生成回复（树莓派）；④ TTS 将回复转为语音（树莓派）；⑤ 喇叭播放、屏幕显示说话表情（ESP32）。

**例 1.2** 修改 curl 命令中的 `text` 字段，发送几条不同内容，观察回复的规律并解释原因。

**例 1.3** 为什么摄像头画面不保存？为什么 API 密钥只存放在树莓派上？

**解**：两者都出于隐私与安全设计。不保存画面是项目隐私规则的硬性要求；ESP32 端可能被拆解或丢失，因此密钥、对话记录等敏感数据一律只存放在底座中。

## 第二章 Python 基础

### 学习目标

掌握变量、字符串、条件、循环、列表、字典、函数、类的基本用法；能读懂项目源码中的 `MockLLM` 类。

本章所有例题都取自项目的真实场景，学完即可直接阅读项目代码。

### 核心概念

**变量与字符串**。变量是有名字的存储位置：`display_name = "张奶奶"`。f-string 用于将变量嵌入文字：`f"{display_name}，您好"`。

**条件判断**。`if / elif / else` 根据条件选择执行路径；条件的值是布尔类型（True/False）。

**列表与循环**。列表按顺序存放多个元素；`for` 循环逐个处理列表元素。

**字典**。以"键—值"方式组织数据：`{"type": "state", "state": "LISTENING"}`。字典与第三章的 JSON 消息结构直接对应。

**函数**。将一段处理逻辑封装为可重复调用的单元：接收输入，返回输出。

**类与对象**。类定义一类事物的属性和行为，对象是按类创建的实例。项目中 `MockLLM` 就是一个类。

**例 2.5（函数，本章重点）** 编写函数 `generate_reply(text, display_name)`，要求：text 去除首尾空白后为空时，返回"我没有听清，您能再说一遍吗？"；display_name 非空时在回复前加称呼；否则返回固定格式回复。

**解**：

```python
def generate_reply(text, display_name=None):

    if not clean:
        return "我没有听清，您能再说一遍吗？"
    greeting = f"{display_name}，" if display_name else ""
    return f"{greeting}我听到您说“{clean}”。谢谢您愿意和我聊聊。"

print(generate_reply("我年轻时在纺织厂上班", "张奶奶"))
```

**解**：

```python
class Robot:

r = Robot()

```

## 第三章 JSON 与通信协议

### 学习目标

理解两端如何通过串口交换结构化消息；能手写、解析并校验项目协议中的消息。

### 核心概念

**JSON**。一种通用的数据交换格式，结构与 Python 字典基本一致，几乎所有编程语言都能读写。

**JSON Lines**。本项目的传输约定：每行一个完整的 JSON 对象，以换行符 `\n` 作为消息结束标志。单条消息内不允许出现裸换行。

**协议**。通信双方共同遵守的约定，包括消息类型、字段名称与取值范围，完整定义见 `docs/PROTOCOL.md`。关键原则：收到不合法的消息应当**丢弃并记录**，但绝不能导致程序退出——机器人不能因为一条坏消息而死机。

常用消息示例：

```json
{"type":"state","state":"LISTENING"}            ← 树莓派→ESP32：切换状态
{"type":"face","emotion":"smile","intensity":0.8} ← 树莓派→ESP32：设置表情
{"type":"event","event":"WAKE_BUTTON_PRESSED"}   ← ESP32→树莓派：唤醒键按下
{"type":"heartbeat","uptime_ms":123456}          ← ESP32→树莓派：心跳上报
```

### 实践步骤

1. 通读 `docs/PROTOCOL.md` 的消息示例部分，了解两个方向各有哪些消息类型。
2. 在 Python 交互环境中练习 `json.dumps`（字典转文本）与 `json.loads`（文本转字典）。
3. 课堂练习：两人一组，一人扮演 ESP32、一人扮演树莓派，在纸上手写 JSON 消息互相传递，接收方须正确说出应执行的动作；写错字段的消息接收方应当拒收。

### 例题

**例 3.1** 老人按下停止按钮，写出 ESP32 发给树莓派的消息。

**解**：`{"type":"event","event":"STOP_BUTTON_PRESSED"}`

**例 3.2** 解析一行收到的消息文本，打印消息类型。

**解**：

```python
import json
line = '{"type":"state","state":"LISTENING"}'
msg = json.loads(line)
print(msg["type"])   # 输出 state
```

**例 3.3** 编写函数 `make_state_line(state)`，返回可直接写入串口的一行文本（含结尾换行符）。

**解**：

```python
import json

def make_state_line(state):
    return json.dumps({"type": "state", "state": state}) + "\n"
```

**例 3.4（本章重点）** 编写函数 `parse_line(line)`：输入合法时返回字典；不是合法 JSON 或缺少 type 字段时，打印警告并返回 None。

**解**：

```python
import json

def parse_line(line):
    try:
        msg = json.loads(line)
    except json.JSONDecodeError:
        print("警告：不是合法 JSON，已丢弃")
        return None
    if "type" not in msg:
        print("警告：缺少 type 字段，已丢弃")
        return None
    return msg
```

注意 try/except 的作用：把"可能出错的解析"包起来，出错时走处理分支而不是让程序崩溃。这正是协议"坏消息不能导致程序退出"要求的实现方式。

不查资料写出"按下唤醒按钮"与"切换到 THINKING 状态"两条消息；能解释为什么每条消息必须独占一行。

## 第四章 状态机

### 学习目标

理解状态机这一核心设计模式：系统任意时刻处于且仅处于一个状态，状态间按预定义规则转移。

### 核心概念

**状态**。协议定义了 15 个设备状态，常用的有：IDLE（待机）、LISTENING（聆听）、THINKING（思考）、SPEAKING（说话）、CONFUSED（未听清）、PRIVACY_MIC_OFF（麦克风关闭）、NETWORK_ERROR（网络异常）等。屏幕表情就是当前状态的可视化。

**状态转移**。标准对话序列为：

```text
IDLE → LISTENING → THINKING → SPEAKING → IDLE
```

**转移规则**。并非任意两个状态间都允许转移。本项目的两条关键规则：麦克风静音时禁止进入 LISTENING；STOP 按键使系统停止当前动作并回到 IDLE。隐私状态具有优先级：静音、遮挡摄像头是独立事实，不会被普通状态切换清除。

### 实践步骤

1. 在纸上绘制 BOOTING、IDLE、LISTENING、THINKING、SPEAKING、PRIVACY_MIC_OFF 六个状态的转移图，箭头上标注触发事件。
2. 课堂练习：教师报出事件序列（按下唤醒键→收到语音→模型返回→播放完毕→拨动静音开关……），学生依次报出系统应处的状态。
3. 完成例题后，对照阅读 `docs/PROTOCOL.md` 中"状态与隐私优先级"一节，检验自己的转移图是否符合规范。

### 例题

**例 4.1** 画出一次完整对话的状态转移图，标注触发事件。

**解**：

```text
IDLE --按下唤醒键--> LISTENING --收到用户话语--> THINKING
     --模型返回回复--> SPEAKING --播放结束--> IDLE
（任意状态 --按下停止键--> IDLE）
```

**例 4.2（本章重点）** 用字典实现允许转移表，编写 `can_transition(current, target)`。

**解**：

```python
ALLOWED = {
    "IDLE": ["LISTENING", "FACE_SCANNING"],
    "LISTENING": ["THINKING", "IDLE"],
    "THINKING": ["SPEAKING", "IDLE"],
    "SPEAKING": ["IDLE"],
}

def can_transition(current, target):
    return target in ALLOWED.get(current, [])

print(can_transition("IDLE", "LISTENING"))   # True
print(can_transition("IDLE", "SPEAKING"))    # False
```

**例 4.3** 增加参数 `mic_muted`：静音时任何状态都不允许进入 LISTENING。

**解**：

```python
def can_transition(current, target, mic_muted=False):
    if target == "LISTENING" and mic_muted:
        return False
    return target in ALLOWED.get(current, [])
```

**例 4.4** 机器人正在说话时老人拨动了静音开关。播放结束后屏幕应显示什么状态？解除静音后为什么不自动恢复录音？

**解**：显示 PRIVACY_MIC_OFF。解除开关后系统回到 IDLE 而非自动开始录音：隐私相关操作遵循"宁可少做、不可多做"的原则，重新录音必须由老人主动按键发起。这是协议文档明确规定的行为。

### 本章要求

独立完成例 4.3；能说明转移规则存在的必要性（防止非法状态切换破坏系统行为与隐私约束）。

## 第五章 Web 后端与 API

### 学习目标

理解服务器/客户端模型与 HTTP 接口；能编写一个最小的 FastAPI 应用；看懂项目 `/chat/text` 接口的定义。

### 核心概念

**服务器与客户端**。后端服务持续运行、等待请求；浏览器、curl 命令、ESP32 串口客户端都是向它发起请求的客户端。

**HTTP 请求**。GET 用于查询（如查询健康状态），POST 用于提交数据（如发送一句话）。请求和响应的正文都使用 JSON。

**API 接口**。服务对外公开的"约定"：地址、方法、请求字段、响应字段。例如 `POST /chat/text` 要求提交 `user_id` 与 `text`，返回 `reply` 与 `state`。

**FastAPI**。本项目使用的 Python Web 框架，自动生成可交互的 `/docs` 文档页面。

### 实践步骤

1. 重新审视第一章的 curl 命令，理解各参数：`-X POST` 指定方法，`-H` 声明内容类型，`-d` 携带 JSON 数据。
2. 在 `/docs` 页面上直接调用 `/chat/text`，观察完整的请求与响应。
3. 完成例 5.2，运行自己的后端服务。
4. 打开 `pi-backend/app/web/routes.py`，找到 `/health` 与 `/chat/text` 的定义位置，观察其结构与例 5.2 的相似性。

### 例题

**例 5.1** 用 curl 分别调用 `/health` 和 `/device/state`，记录返回内容并解释各字段。

**解**：`/health` 返回 `{"status":"ok"}`，表示服务正常。`/device/state` 返回形如 `{"state":"IDLE","mic_muted":false,"camera_blocked":false,"current_user_id":null}`：当前设备状态、两个隐私开关的事实状态、当前识别到的用户。

**例 5.2（本章重点）** 编写最小 FastAPI 应用：`GET /health` 返回 `{"status":"ok"}`；`POST /echo` 接收 `{"text":"..."}`，返回 `{"reply":"你说的是：..."}`。

**解**（保存为 `mini_app.py`，以 `uvicorn mini_app:app --port 8001` 运行）：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class EchoIn(BaseModel):
    text: str

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/echo")
def echo(body: EchoIn):
    return {"reply": f"你说的是：{body.text}"}
```

**例 5.3** 将 `/echo` 改为 `/chat`，内部调用第二章编写的 `generate_reply` 函数，使返回格式与项目一致。

**解**：返回语句改为 `return {"reply": generate_reply(body.text), "state": "SPEAKING"}`。至此你已实现了项目 `/chat/text` 接口的简化版本。

**例 5.4** 为什么 ESP32 不直接调用外部大模型 API，而必须经由树莓派中转？

**解**：① API 密钥只能保存在树莓派上，避免泄露；② ESP32 的算力与内存不足以承担网络加密通信与复杂调度；③ 对话必须由底座统一调度，才能完成存储、状态控制与记忆检索。

### 本章要求

自己编写的后端能通过 curl 正常响应；能完整说明 `/chat/text` 请求与响应中每个字段的含义。

## 第六章 数据库

### 学习目标

理解数据持久化的意义；掌握基础 SQL 查询；能查看项目保存的对话记录。

### 核心概念

**持久化**。内存中的变量随程序退出而消失；数据库将数据写入硬盘，重启后仍然存在。机器人"记得"昨天的对话，依靠的就是数据库。

**表、行、列**。关系型数据库以表格组织数据。核心表 `conversation_turns` 的主要字段：user_id（用户）、role（user 或 assistant，即这句话是谁说的）、text（内容）、created_at（时间）、should_remember（是否进入长期记忆）、privacy_level（隐私级别）。

**SQLite**。整个数据库存放于单个文件中的轻量级数据库，适合本项目的单机场景。

**SQL**。查询数据库的标准语言。本章使用四个关键字：SELECT（选取）、WHERE（筛选）、ORDER BY（排序）、COUNT（计数）。

### 实践步骤

1. 先通过 `/chat/text` 发送若干对话，产生数据。
2. 用 `sqlite3` 打开数据库文件，执行 `.tables` 查看所有表。
3. 用 SQL 查询刚才的对话记录。
4. 阅读 `docs/DATABASE.md`，了解其余各表（users、memory_facts、life_events、autobiography_chapters），理解"对话 → 记忆 → 人生事件 → 自传章节"的数据流水线。

### 例题

**例 6.1** 查询 user_001 的全部对话，按时间排序。

**解**：

```sql
SELECT role, text, created_at FROM conversation_turns
WHERE user_id = 'user_001' ORDER BY created_at;
```

**例 6.2** 统计 user_001 说过多少句话（仅统计 role 为 user 的行）。

**解**：

```sql
SELECT COUNT(*) FROM conversation_turns
WHERE user_id = 'user_001' AND role = 'user';
```

**例 6.3** `should_remember` 字段的作用是什么？没有它会违反哪条项目规则？

**解**：当老人表示"这个不要记"时，该轮对话被标记为 should_remember=false，不进入长期记忆和自传。缺少该字段将无法落实项目隐私规则第 8 条："老人说'不记这个'时，该轮对话不进入长期记忆。"

**例 6.4（设计题）** 若要支持"记住老人最爱听的戏曲"，应如何存储？

**解**（参考）：无需新建表，存入 memory_facts，fact_type 取 'preference'，content 记录具体内容（如"爱听越剧《梁祝》"）。良好的表设计应能容纳新需求而不必修改结构。

### 本章要求

能独立查询出自己产生的对话记录；能完整叙述一句话从输入到入库的路径（接口 → 服务层 → 数据表）。

## 第七章 Mock 与系统联调

### 学习目标

理解 Mock 在工程中的价值；在无硬件条件下完成"按键触发完整对话"的联调；掌握自动化测试的基本用法。

### 核心概念

**Mock（模拟实现）**。与真实组件接口一致、内部简化的替代品。项目中包括：MockLLM（模拟大模型）、MockSTT / MockTTS（模拟语音识别与合成）、`tools/mock_esp32.py`（在电脑上模拟整个 ESP32 设备）。

**接口与实现分离**。由于其余代码只依赖接口，后续将 Mock 替换为真实实现时无需改动调用方。这是本项目架构的核心设计。

**自动化测试**。`make test` 一次性运行全部测试用例，检查功能是否被意外破坏。修改代码前后都应运行测试。

### 实践步骤

1. 启动设备模拟器：`make mock-esp32`（后端需按 `tools/README.md` 配置为 mock_tcp 传输模式）。
2. 在模拟器交互终端输入 `wake`，相当于按下唤醒键。
3. 在另一终端反复执行 `curl http://127.0.0.1:8000/device/state`，观察状态依次流转：LISTENING → THINKING → SPEAKING → IDLE。
4. 依次尝试 `stop`、`mic mute`、`camera block` 命令，验证第三、四章所学的消息与转移规则。
5. 运行 `make test`，确认全部测试通过。

### 例题

**例 7.1** 用模拟器触发一次完整对话，记录状态流转顺序，并在数据库中定位这轮对话。

**解**：状态依次为 LISTENING → THINKING → SPEAKING → IDLE；数据库 conversation_turns 表新增两行，role 分别为 user 与 assistant。

**例 7.2（破坏性实验）** 故意修改 `chat_client.py` 中 MockLLM 的回复模板，运行 `make test` 观察结果，再还原。

**解**：与聊天相关的测试用例失败，报错信息明确给出期望值与实际值的差异。结论：测试是修改代码的安全网；实验后用 `git checkout .` 还原。

**例 7.3（本章重点）** 为 MockLLM 增加规则：用户话语包含"纺织厂"时，回复"纺织厂的故事我很想多听听，那是哪一年的事呀？"

**解**：在 `generate_reply` 中、模板回复之前加入：

```python
if "纺织厂" in clean_text:
    return f"{greeting}纺织厂的故事我很想多听听，那是哪一年的事呀？"
```

修改后运行测试；若有用例失败，判断是功能被破坏还是测试预期需要同步更新。这条规则正是"温和追问时间、地点、人物"的雏形——真实 LLM 的系统提示词中就有这一要求。

**例 7.4** 为什么项目不直接使用真硬件、真大模型，而先构建整套模拟实现？

**解**：真实硬件与外部 API 引入成本、延迟和不确定性，多个变量混杂时难以定位问题。先以 Mock 验证系统骨架的正确性，再逐个替换，每次只引入一个新变量——相当于工程中的控制变量法。

### 本章要求

独立完成模拟器联调并讲解状态流转；例 7.3 的修改通过全部测试。

## 第八章 ESP32 固件基础

> 无开发板时完成前两节（读代码部分）；有开发板时完成全部内容。

### 学习目标

认识单片机与 C 语言的基本形态；读懂固件中状态定义与心跳上报的代码；有硬件条件时完成编译、烧录和表情修改。

### 核心概念

**单片机**。面向单一任务的微型计算机，无操作系统界面，程序烧录后持续运行。本项目使用 ESP32-S3。

**C 语言与 Python 的差异**。C 要求显式声明变量类型，代码需编译为机器指令后才能运行；换来的是更小的体积和更高的运行效率，适合资源受限的单片机。

**固件模块划分**。状态管理（app_state）、协议编解码（protocol）、界面适配（ui）、按键输入（input）、串口通信与心跳（comms）——与后端的模块化思想一致。其中 ui 层是可替换的硬件适配层：换不同的屏幕只需重写这一层，其余代码不动。

**心跳**。ESP32 定时上报 `{"type":"heartbeat","uptime_ms":...}`，供树莓派判断设备是否在线。

**烧录**。将编译好的程序通过 USB 写入开发板 Flash 的过程。基本流程：`idf.py build`（编译）→ `idf.py flash`（烧录）→ `idf.py monitor`（查看串口输出）。

### 实践步骤

1. 打开 `esp32-firmware/main/app_state.h`，将其中的 C 状态枚举与 `docs/PROTOCOL.md` 的状态列表逐一对照。
2. 阅读 `main/comms/heartbeat.c`，理解定时上报的实现。
3. （有开发板）安装 ESP-IDF，按 `esp32-firmware/README.md` 编译烧录，在监视器中确认心跳消息。注意：编译前需将固件目录复制到不含中文的路径。
4. （有开发板）修改一个表情参数，重新编译烧录，观察屏幕变化。

### 例题

**例 8.1** 对比以下两行等价代码，指出三处写法差异：

```python
state = "IDLE"        # Python
```

```c
app_state_t state = APP_STATE_IDLE;   /* C */
```

**解**：① C 必须声明变量类型（`app_state_t`）；② C 使用枚举常量而非字符串表示状态；③ C 语句以分号结尾，注释语法也不同。

**例 8.2** 在固件源码中找到定义全部状态的文件，核对状态数量是否与协议文档一致。

**解**：定义位于 `main/app_state.h`，与协议文档的 15 个状态一一对应。协议是两端共同遵守的约定，任何一端擅自增删状态都会导致通信失败。

**例 8.3** 心跳中的 `uptime_ms` 为什么采用"开机以来的毫秒数"而不是当前时刻？

**解**：ESP32 无后备电池时钟，断电后无法得知墙上时间；而开机时长来自单调时钟，只增不跳变，用于判断设备存活更可靠。

**例 8.4（有开发板）** 将开机默认表情改为另一种，编译烧录验证。

**解**：在 `ui/` 目录中定位 IDLE 状态对应的表情绘制调用并替换，执行 `idf.py build flash` 后上电观察。本题的重点是完整走通"修改 → 编译 → 烧录 → 验证"的嵌入式开发循环。

### 本章要求

能说明固件五个模块的职责；有开发板时独立完成一次表情修改与烧录。

前八章覆盖了系统的现有实现（Phase 0–2 及联调）。本章为开放性专题，对应项目规划中的 Phase 3–7，任选方向深入：

## 附录B 常见问题排查

| 现象 | 可能原因 | 处理方法 |
|---|---|---|
| `make run` 报找不到模块 | 未执行 `make setup` | 重新执行 setup |
| curl 无响应 | 服务未启动或地址错误 | 确认服务运行中，地址为 127.0.0.1:8000 |
| 中文显示乱码 | 终端编码问题 | 将终端设置为 UTF-8 |
| 测试失败 | 之前实验的修改未还原 | `git status` 检查并还原 |
| ESP-IDF 编译报路径错误 | 路径含中文或空格 | 将固件目录复制到纯英文路径 |
