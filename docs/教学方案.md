# 老人陪伴对话机器人 · 中学生教学方案

> 适用对象：零编程基础的中学生
> 教学目标：完整跟做本项目，最终能独立运行、修改并讲解这个机器人
> 建议总课时：约 30–36 课时（每课时 45–60 分钟），可按 1 学期每周 2 次课安排

---

## 〇、项目剖析

### 这个项目是什么

一个面向老人的桌面陪伴机器人，能语音聊天、显示表情、识别人脸、保存对话，并逐步生成老人的"人生自传"。

### 系统由三大块组成

```text
┌─────────────────────────┐
│ 机器人头部（ESP32-S3）    │  负责：显示表情、按键、麦克风、喇叭
│ esp32-firmware/ (C语言)  │  ——"脸和耳朵嘴巴"
└──────────┬──────────────┘
           │ USB 串口，每行一条 JSON 消息
┌──────────▼──────────────┐
│ 底座（树莓派5）           │  负责：听懂(STT)、思考(LLM)、说话(TTS)、
│ pi-backend/ (Python)     │  记忆(数据库)、认人(人脸识别)
└─────────────────────────┘  ——"大脑"

tools/mock_esp32.py：没有硬件时，用它在电脑上"假装"是机器人头部
```

### 项目当前进度（Phase 0–2 已完成）

- 后端 FastAPI 服务可运行，`/chat/text` 可对话（用 MockLLM 假模型回复）
- SQLite 数据库保存每轮对话
- 设备状态机（IDLE、LISTENING、THINKING、SPEAKING……15 个状态）
- 串口 JSON Lines 协议 + Python 客户端 + ESP32 固件骨架
- 真实语音、人脸识别、自传生成属于后续 Phase 3–7

### 教学总路线

零基础学生不能直接读项目代码，所以路线是：**先用项目里的真实场景教 Python 基础，再一层层揭开项目本身**。

| 阶段 | 主题 | 课时 | 对应项目部分 |
|---|---|---|---|
| 一 | 认识项目与环境搭建 | 2 | 整体 |
| 二 | Python 零基础入门 | 10 | 为读懂后端做准备 |
| 三 | JSON 与通信协议 | 3 | docs/PROTOCOL.md |
| 四 | 状态机 | 3 | app/device/ |
| 五 | Web 后端与 API | 4 | app/main.py、app/web/ |
| 六 | 数据库 | 3 | app/db/ |
| 七 | Mock 与整体联调 | 3 | MockLLM、tools/mock_esp32.py |
| 八 | ESP32 硬件初步 | 4 | esp32-firmware/ |
| 九 | 进阶展望（选修） | 2+ | Phase 4–7 |

每阶段包含：**教学目标 → 核心概念 → 教学步骤 → 例题（含参考答案）→ 验收标准**。

## 阶段一：认识项目与环境搭建（2 课时）

### 教学目标

学生能说出机器人"头"和"大脑"各自负责什么，并在电脑上把后端跑起来、完成第一次对话。

### 核心概念

1. **分工思想**：ESP32 负责"显示、采集、播放"，树莓派负责"听懂、思考、存储"。类比：ESP32 是脸和五官，树莓派是大脑。
2. **原型开发**：先用"假的"（mock）零件把流程跑通，再逐个换成真的。就像先用纸板做汽车模型确定形状，再造真车。
3. **终端/命令行**：和电脑对话的文字窗口。

### 教学步骤

1. 演示：给学生看项目 README 和架构图，提问"如果机器人听不清，问题可能出在头还是大脑？"
2. 带学生打开终端，练习 `cd`、`ls` 进入项目目录。
3. 一起执行：

   ```bash
   make setup
   cp pi-backend/.env.example pi-backend/.env
   make run
   ```

4. 浏览器打开 `http://127.0.0.1:8000/docs`，见到 API 文档页面。
5. 新开终端，发出第一次对话：

   ```bash
   curl -X POST http://127.0.0.1:8000/chat/text \
     -H 'Content-Type: application/json' \
     -d '{"user_id":"user_001","text":"你好呀"}'
   ```

6. 观察返回的回复，庆祝"机器人活了"。

### 例题

**例 1-1（口头）**：老人对机器人说"我年轻时在纺织厂上班"，请按顺序说出这句话在系统里经过的 5 个环节。

> 参考答案：① 麦克风采集声音（ESP32）→ ② 语音变文字 STT（树莓派）→ ③ 大模型 LLM 想出回复（树莓派）→ ④ 文字变语音 TTS（树莓派）→ ⑤ 喇叭播放 + 屏幕显示说话表情（ESP32）。

**例 1-2（动手）**：把 curl 命令里的 `text` 改成你想说的另一句话，再发送一次，观察回复有什么规律。

> 参考答案：回复总是"我听到您说'……'。谢谢您愿意和我聊聊。"——因为现在用的是 MockLLM（假模型），它只会按固定模板回复。这正是"先用假零件跑通流程"的体现。

**例 1-3（思考）**：为什么摄像头拍到的画面不保存、API 密钥只放在树莓派上？

> 参考答案：保护老人隐私；ESP32 可能被拆开或丢失，敏感信息只放在更安全的"大脑"里。

### 验收标准

学生能独立启动服务、用 curl 完成一次对话，并向别人讲清"头"和"大脑"的分工。

## 阶段二：Python 零基础入门（10 课时）

> 全部例子都来自本项目的真实场景，学生学完就能看懂项目里最简单的文件。

### 教学目标

掌握变量、字符串、条件、循环、列表、字典、函数、类的基本用法，能读懂并仿写 `MockLLM` 这样的小类。

### 核心概念与教学步骤（按课时拆分）

**第 1–2 课时：变量与字符串**

- 概念：变量是"贴了名字的盒子"；字符串是文字。
- 用 f-string 拼接欢迎语（项目中 MockLLM 就是这么做的）。

**第 3–4 课时：条件判断**

- `if / elif / else`；布尔值 True/False。
- 场景：麦克风静音时不许进入"聆听"状态（项目的真实规则）。

**第 5 课时：列表与循环**

- 列表存多轮对话；`for` 循环逐条处理。

**第 6 课时：字典**

- 字典是"带标签的盒子组"，正好对应 JSON 消息（为阶段三铺垫）。

**第 7–8 课时：函数**

- 函数是"可以反复使用的小机器"：输入 → 加工 → 输出。
- 仿写项目里的 `generate_reply`。

**第 9–10 课时：类与对象**

- 类是"图纸"，对象是"照图纸造出来的东西"。
- 读项目真实代码 `pi-backend/app/llm/chat_client.py` 里的 `MockLLM` 类。

### 例题

**例 2-1（变量与字符串）**：机器人认出了张奶奶，请用变量和 f-string 打印"张奶奶，欢迎回来！"

> 参考答案：
>
> ```python
> display_name = "张奶奶"
> print(f"{display_name}，欢迎回来！")
> ```

**例 2-2（条件）**：写一段代码：如果 `mic_muted` 是 True，打印"麦克风已静音，不能聆听"；否则打印"开始聆听"。

> 参考答案：
>
> ```python
> mic_muted = True
> if mic_muted:
>     print("麦克风已静音，不能聆听")
> else:
>     print("开始聆听")
> ```
>
> 教师点拨：这就是项目协议文档里"`mic_muted=true` 时禁止进入 LISTENING"的规则。

**例 2-3（循环与列表）**：下面是老人今天说过的三句话，用循环逐句打印"第 x 句：……"。

> 参考答案：
>
> ```python
> turns = ["我年轻时在纺织厂上班", "厂子在杭州", "那时候认识了你李爷爷"]
> for i, text in enumerate(turns, start=1):
>     print(f"第 {i} 句：{text}")
> ```

**例 2-4（字典）**：用字典表示一条"机器人进入聆听状态"的消息，包含 type 和 state 两个键，然后打印出 state 的值。

> 参考答案：
>
> ```python
> msg = {"type": "state", "state": "LISTENING"}
> print(msg["state"])   # LISTENING
> ```

**例 2-5（函数，重点题）**：仿照项目的 MockLLM，写一个函数 `generate_reply(text, display_name)`：
- 若 text 去掉空格后是空的，返回"我没有听清，您能再说一遍吗？"
- 若 display_name 不为空，回复开头加上称呼
- 否则回复"我听到您说'xxx'。谢谢您愿意和我聊聊。"

> 参考答案：
>
> ```python
> def generate_reply(text, display_name=None):
>     clean = text.strip()
>     if not clean:
>         return "我没有听清，您能再说一遍吗？"
>     greeting = f"{display_name}，" if display_name else ""
>     return f"{greeting}我听到您说“{clean}”。谢谢您愿意和我聊聊。"
>
> print(generate_reply("我年轻时在纺织厂上班", "张奶奶"))
> ```
>
> 做完后打开 `pi-backend/app/llm/chat_client.py`，对照真实代码，学生会发现自己已经能读懂它。

**例 2-6（类）**：写一个 `Robot` 类：属性 `state` 初始为 "IDLE"；方法 `set_state(new_state)` 修改状态并打印"状态切换为 xxx"。

> 参考答案：
>
> ```python
> class Robot:
>     def __init__(self):
>         self.state = "IDLE"
>
>     def set_state(self, new_state):
>         self.state = new_state
>         print(f"状态切换为 {new_state}")
>
> r = Robot()
> r.set_state("LISTENING")
> ```

### 验收标准

学生不看答案能完成例 2-5，并能指着 `chat_client.py` 说出每一行的作用。

## 阶段三：JSON 与通信协议（3 课时）

### 教学目标

理解"头"和"大脑"如何隔着一根 USB 线对话，能手写和解析项目协议中的消息。

### 核心概念

1. **JSON**：一种双方都认识的"消息格式"，长得和 Python 字典几乎一样。
2. **JSON Lines 协议**：一行一条消息，用换行符 `\n` 表示"我说完了"。类比：两人传纸条，约定一张纸条只写一句话。
3. **协议要双方遵守**：字段名、取值范围都是约好的（见 `docs/PROTOCOL.md`），任何一方乱写，对方就"听不懂"并丢弃这条消息。

### 教学步骤

1. 一起读 `docs/PROTOCOL.md` 的消息示例（不必读约束细节）。
2. 演示 `json.dumps`（字典→文字）和 `json.loads`（文字→字典）。
3. 玩"传纸条游戏"：一名学生扮演 ESP32，一名扮演树莓派，在纸上手写 JSON 互发，对方要正确"执行"（做出表情/报出状态）。
4. 上机完成例题。

### 例题

**例 3-1（手写消息）**：老人按下了停止按钮，请写出 ESP32 应发给树莓派的那一行 JSON。

> 参考答案：`{"type":"event","event":"STOP_BUTTON_PRESSED"}`

**例 3-2（解析）**：用 Python 解析收到的一行消息，并打印消息类型。

> 参考答案：
>
> ```python
> import json
> line = '{"type":"state","state":"LISTENING"}'
> msg = json.loads(line)
> print(msg["type"])   # state
> ```

**例 3-3（生成）**：写函数 `make_state_line(state)`，返回可以直接从串口发出的一行文本（末尾带换行符）。

> 参考答案：
>
> ```python
> import json
>
> def make_state_line(state):
>     return json.dumps({"type": "state", "state": state}) + "\n"
>
> print(repr(make_state_line("SPEAKING")))
> ```

**例 3-4（容错，思考+编码）**：如果收到的一行缺少 `type` 字段，程序应该怎么办？先讨论，再写代码：合法则返回字典，不合法则返回 None 并打印警告。

> 参考答案：
>
> ```python
> import json
>
> def parse_line(line):
>     try:
>         msg = json.loads(line)
>     except json.JSONDecodeError:
>         print("警告：不是合法 JSON，丢弃")
>         return None
>     if "type" not in msg:
>         print("警告：缺少 type 字段，丢弃")
>         return None
>     return msg
> ```
>
> 教师点拨：协议文档规定"坏消息要丢弃并记录，但不能让程序崩溃退出"——机器人不能因为一条坏消息就死机。

### 验收标准

学生能不查资料写出"按下唤醒按钮"和"切换到 THINKING 状态"两条消息，并解释为什么每条消息必须独占一行。

## 阶段四：状态机（3 课时）

### 教学目标

理解"状态机"这一核心设计：机器人任何时刻只处于一个状态，状态之间按规则切换。

### 核心概念

1. **状态**：机器人的 15 个状态（IDLE 待机、LISTENING 聆听、THINKING 思考、SPEAKING 说话、CONFUSED 疑惑……）。类比：人也有"睡觉/吃饭/上课"等状态，不能同时既睡觉又上课。
2. **状态转移**：一次普通对话是 `IDLE → LISTENING → THINKING → SPEAKING → IDLE`。
3. **转移规则**：不是任意两个状态都能互相切换。比如麦克风静音时禁止进入 LISTENING；按下停止按钮总是回到 IDLE。

### 教学步骤

1. 学生在纸上画出 15 个状态里最重要的 6 个（BOOTING、IDLE、LISTENING、THINKING、SPEAKING、PRIVACY_MIC_OFF），并画箭头表示转移。
2. 角色扮演：教师喊事件（"按下唤醒键！""模型回复了！""拨了静音开关！"），学生报出机器人应处的状态。
3. 用字典实现一个迷你状态机（例 4-2）。
4. 对照阅读 `docs/PROTOCOL.md` 的"状态与隐私优先级"一节。

### 例题

**例 4-1（画图）**：画出一次完整对话的状态转移图，并标注触发每次转移的事件。

> 参考答案：
>
> ```text
> IDLE --按下唤醒键--> LISTENING --说完话/收到文本--> THINKING
>      --模型给出回复--> SPEAKING --播放结束--> IDLE
> （任意状态 --按下停止键--> IDLE）
> ```

**例 4-2（编码，重点题）**：用字典写出允许的转移表，并实现 `can_transition(current, target)`。

> 参考答案：
>
> ```python
> ALLOWED = {
>     "IDLE": ["LISTENING", "FACE_SCANNING"],
>     "LISTENING": ["THINKING", "IDLE"],
>     "THINKING": ["SPEAKING", "IDLE"],
>     "SPEAKING": ["IDLE"],
> }
>
> def can_transition(current, target):
>     return target in ALLOWED.get(current, [])
>
> print(can_transition("IDLE", "LISTENING"))   # True
> print(can_transition("IDLE", "SPEAKING"))    # False
> ```

**例 4-3（加规则）**：给例 4-2 增加参数 `mic_muted`：静音时任何状态都不许进入 LISTENING。

> 参考答案：
>
> ```python
> def can_transition(current, target, mic_muted=False):
>     if target == "LISTENING" and mic_muted:
>         return False
>     return target in ALLOWED.get(current, [])
> ```

**例 4-4（思考）**：老人在机器人说话时拨了静音开关，说完话后机器人应该显示什么状态？为什么解除静音后不自动恢复录音？

> 参考答案：显示 PRIVACY_MIC_OFF。解除开关后应回到安全的 IDLE 而不是自动开始录音——隐私操作必须"宁可少做，不可多做"，重新录音应由老人主动按键发起。

### 验收标准

学生能独立完成例 4-3，并用自己的话解释"为什么需要转移规则，而不是想切就切"。

## 阶段五：Web 后端与 API（4 课时）

### 教学目标

理解"服务"和"接口"的概念，能写一个最小的 FastAPI 应用，并看懂项目的 `/chat/text` 接口。

### 核心概念

1. **服务器/客户端**：后端是一直开着的"服务窗口"，别人（浏览器、curl、ESP32 客户端）来"提交表格"，它返回结果。
2. **HTTP 请求**：GET（查询）和 POST（提交数据）；请求和响应的正文都是 JSON。
3. **API 接口**：约定好的窗口地址和表格格式，如 `POST /chat/text` 要提交 `user_id` 和 `text`。
4. **FastAPI**：Python 里搭这种窗口的工具，自带 `/docs` 交互文档。

### 教学步骤

1. 复跑阶段一的 curl 命令，这次逐个讲解 `-X POST`、`-H`、`-d` 的含义。
2. 打开 `http://127.0.0.1:8000/docs`，用网页界面直接调用 `/chat/text`，观察请求和响应。
3. 新建文件写一个最小 FastAPI 应用（例 5-2），用 `uvicorn` 运行。
4. 对照阅读 `pi-backend/app/web/routes.py` 中 `/health` 和 `/chat/text` 的定义（只求看懂结构）。

### 例题

**例 5-1（动手）**：分别用 curl 调用 `/health` 和 `/device/state`，写下返回的 JSON，并解释每个字段。

> 参考答案：`/health` 返回 `{"status":"ok"}` 表示服务活着；`/device/state` 返回当前状态、麦克风/摄像头隐私开关和当前用户，如 `{"state":"IDLE","mic_muted":false,"camera_blocked":false,"current_user_id":null}`。

**例 5-2（编码，重点题）**：写一个最小 FastAPI 应用，含两个接口：`GET /health` 返回 `{"status":"ok"}`；`POST /echo` 接收 `{"text":"..."}` 并返回 `{"reply":"你说的是：..."}`。

> 参考答案（保存为 `mini_app.py`，运行 `uvicorn mini_app:app --port 8001`）：
>
> ```python
> from fastapi import FastAPI
> from pydantic import BaseModel
>
> app = FastAPI()
>
> class EchoIn(BaseModel):
>     text: str
>
> @app.get("/health")
> def health():
>     return {"status": "ok"}
>
> @app.post("/echo")
> def echo(body: EchoIn):
>     return {"reply": f"你说的是：{body.text}"}
> ```

**例 5-3（改造）**：把例 5-2 的 `/echo` 改成 `/chat`，内部调用阶段二写的 `generate_reply` 函数——你就拥有了一个迷你版对话后端。

> 参考答案：把返回行改为 `return {"reply": generate_reply(body.text), "state": "SPEAKING"}`，与项目真实接口的返回格式一致。

**例 5-4（思考）**：为什么 ESP32 不直接调用外部大模型 API，而要通过树莓派中转？

> 参考答案：① API 密钥只能存在树莓派上，防泄露；② ESP32 算力和内存太小；③ 统一由大脑调度，便于保存对话和控制状态。

### 验收标准

学生的迷你对话后端能用 curl 成功对话，并能说出项目 `/chat/text` 请求和响应中每个字段的含义。

## 阶段六：数据库（3 课时）

### 教学目标

理解数据为什么要持久化，能用 SQL 查看项目保存的对话记录。

### 核心概念

1. **持久化**：程序关掉后数据还在。变量在内存里（断电即失），数据库在硬盘上。
2. **表、行、列**：像 Excel 表格。项目核心表 `conversation_turns`：每行是一轮对话，列有 user_id、role（谁说的）、text、created_at、should_remember 等。
3. **SQLite**：装在一个文件里的小数据库，适合本项目。
4. **隐私字段**：`should_remember`（老人说"不记这个"时设为 False）、`privacy_level`。

### 教学步骤

1. 提问导入："机器人重启后还记得昨天聊了什么吗？靠什么记住？"
2. 先跑几次 `/chat/text` 造数据，再用 `sqlite3` 打开数据库文件查看。
3. 教 4 条基本 SQL：`SELECT`、`WHERE`、`ORDER BY`、`COUNT`。
4. 对照 `docs/DATABASE.md` 认识其余的表（users、memory_facts、autobiography_chapters），理解"对话 → 记忆 → 事件 → 自传"的数据流水线。

### 例题

**例 6-1（查询）**：写 SQL 查出 user_001 的全部对话，按时间排序。

> 参考答案：
>
> ```sql
> SELECT role, text, created_at FROM conversation_turns
> WHERE user_id = 'user_001' ORDER BY created_at;
> ```

**例 6-2（统计）**：统计 user_001 一共说了多少句话（只算 role 为 user 的行）。

> 参考答案：
>
> ```sql
> SELECT COUNT(*) FROM conversation_turns
> WHERE user_id = 'user_001' AND role = 'user';
> ```

**例 6-3（设计思考）**：为什么 conversation_turns 表需要 `should_remember` 字段？如果没有它会发生什么？

> 参考答案：老人说"不记这个"时，这轮对话仍会短暂存在（用于当次回复），但被标记为不进入长期记忆和自传。没有它，就无法尊重老人"这段别记下来"的意愿，违反项目隐私规则第 8 条。

**例 6-4（设计练习）**：如果要加一个"老人最爱听的歌"功能，你会在哪张表加什么字段？或者新建什么表？

> 参考答案（开放题）：可在 memory_facts 中用 `fact_type='preference'` 保存，如 content="爱听越剧《梁祝》"——这体现了好的表设计能容纳新需求而不必改结构。

### 验收标准

学生能独立查出自己刚才和机器人聊的记录，并讲清一条数据从"说出口"到"进数据库"的路径。

## 阶段七：Mock 与整体联调（3 课时）

### 教学目标

理解 Mock（假替身）的工程价值，完成"按下按钮 → 完整对话流程"的无硬件联调，会跑自动化测试。

### 核心概念

1. **Mock**：真零件还没准备好时的"假替身"，接口一样、内部简化。项目里有 MockLLM（假大模型）、MockSTT、MockTTS、mock_esp32.py（假机器人头）。
2. **接口不变，实现可换**：将来换成真 LLM 时，其他代码一行都不用改——这就是"清晰边界"的威力。
3. **自动化测试**：`make test` 一键检查所有功能有没有被改坏。

### 教学步骤

1. 演示 `tools/mock_esp32.py`：先 `make mock-esp32` 启动模拟器（并按 `tools/README.md` 将后端配置为 mock_tcp 传输），在模拟器交互终端输入 `wake` "按下"唤醒按钮，观察后端状态依次流转 IDLE → LISTENING → THINKING → SPEAKING → IDLE。模拟器还支持 `stop`、`mic mute`、`camera block` 等命令，正好对应阶段三、四学过的消息和规则。
2. 学生自己操作一遍，同时用 `GET /device/state` 在另一个终端观察状态变化。
3. 运行 `make test`，看全部测试通过。
4. 做例 7-2 的"故意改坏"实验，体会测试的保护作用。

### 例题

**例 7-1（动手）**：用 mock_esp32 触发一次完整对话，记录状态流转顺序，并到数据库里找到这轮对话。

> 参考答案：状态依次为 LISTENING → THINKING → SPEAKING → IDLE；数据库中新增两行（role=user 和 role=assistant）。

**例 7-2（实验）**：把 `chat_client.py` 中 MockLLM 的回复模板故意改错（比如删掉引号里的内容），运行 `make test`，观察哪些测试失败；再改回来，测试恢复通过。

> 参考答案：与聊天相关的测试会失败并明确指出期望值与实际值的差异。结论：测试是"安全网"，改代码前后都要跑测试。

**例 7-3（编码）**：给 MockLLM 加一个新本领：如果老人的话里含有"纺织厂"，回复"纺织厂的故事我很想多听听，那是哪一年的事呀？"。改完跑测试，若有失败，思考是否需要更新测试。

> 参考答案：在 `generate_reply` 开头加：
>
> ```python
> if "纺织厂" in clean_text:
>     return f"{greeting}纺织厂的故事我很想多听听，那是哪一年的事呀？"
> ```
>
> 教师点拨：这其实就是"追问时间、地点、人物"的雏形——真 LLM 的系统提示词里正有这条要求。

**例 7-4（思考）**：为什么项目不先接真硬件、真大模型，而先做一套假的？

> 参考答案：真硬件和真 API 又贵又慢又容易出错，会让问题混在一起难以定位。先用 mock 把"骨架"验证正确，再逐个替换，每次只引入一个新变量——这是工程上的"控制变量法"。

### 验收标准

学生能独立完成 mock 联调并讲解状态流转；例 7-3 的修改能通过测试。

## 阶段八：ESP32 硬件初步（4 课时）

> 无开发板时可只上前 2 课时（读代码）；有微雪 ESP32-S3-Touch-AMOLED-1.43C 开发板时上满 4 课时。

### 教学目标

认识单片机与 C 语言的样子，能读懂固件中状态和心跳的核心片段；有板子时能编译烧录并改一个表情。

### 核心概念

1. **单片机**：一台"专心做一件事"的小电脑，没有操作系统界面，程序烧进去就一直跑。
2. **C 语言 vs Python**：C 要声明类型、要编译，换来的是小体积和高速度——适合小内存的 ESP32。
3. **固件**：烧录进单片机的程序。项目固件分为状态（app_state）、协议解析（protocol）、界面（ui）、按键（input）、通信（comms）几个模块，和后端的模块划分思想一致。
4. **心跳**：ESP32 定时发 `{"type":"heartbeat","uptime_ms":...}`，让树莓派知道"我还活着"。

### 教学步骤

1. 对比阅读：把 Python 的状态枚举和 `esp32-firmware/main/app_state.h` 里的 C 枚举放在一起看，学生会发现"两边必须一字不差"。
2. 带读 `main/comms/heartbeat.c`（很短），理解定时上报。
3. （有板子）安装 ESP-IDF，按 `esp32-firmware/README.md` 编译烧录，看串口输出。
4. （有板子）修改 `ui_faces.c` 中某个表情参数，重新烧录，观察屏幕变化。

### 例题

**例 8-1（对比阅读）**：下面是同一个意思的 Python 和 C 代码，找出 3 处写法差异。

> ```python
> state = "IDLE"        # Python
> ```
>
> ```c
> app_state_t state = APP_STATE_IDLE;   /* C */
> ```
>
> 参考答案：① C 必须写出类型 `app_state_t`；② C 用枚举常量而非字符串；③ C 语句以分号结尾、注释写法不同。

**例 8-2（读代码）**：在 `esp32-firmware/main/` 中找到定义所有状态的文件，数一数固件支持几个状态，是否与协议文档中的 15 个一致。

> 参考答案：在 `app_state.h` 中；应与 `docs/PROTOCOL.md` 的状态列表一一对应——协议是两边共同的"合同"。

**例 8-3（思考）**：心跳里的 `uptime_ms` 是"开机以来的毫秒数"而不是北京时间，为什么？

> 参考答案：ESP32 没有电池时钟，断电后不知道现在几点；而"开机以来过了多久"永远单调递增、不会跳变，用来判断设备是否活着更可靠。

**例 8-4（动手，需板子）**：把开机后的默认表情从微笑改成另一种，编译烧录验证。

> 参考答案：在 `ui_faces.c` / `ui_states.c` 中找到 IDLE 状态对应的表情绘制调用并替换，重新 `idf.py build flash`。关键收获是走通"改代码 → 编译 → 烧录 → 上电验证"的完整循环。

### 验收标准

学生能说出固件五个模块的职责；有板子时能独立完成一次"改表情并烧录"。

## 阶段九：进阶展望（选修，2 课时起）

### 教学目标

了解项目未完成的 Phase 3–7 要做什么，选择一个方向做探究式小课题。

### 内容与课题建议

1. **真实串口联调（Phase 3）**：把 mock_esp32 换成真开发板，需要处理重连、握手。课题：设计"两边刚连上时怎么确认对方版本"的握手消息。
2. **人脸识别（Phase 4）**：用 OpenCV 在电脑上先做实验。课题：用笔记本摄像头实现"检测到人脸就打印欢迎语"。
3. **真实大模型（Phase 5）**：把 MockLLM 换成真 API。课题：对比 mock 与真模型的回复差异；讨论系统提示词里"不要编造老人经历""每次最多追问一个问题"为什么重要。

## 附录A：教学建议

1. **每课一跑**：每节课都让项目跑起来一次，保持"这是活的系统"的感觉。
2. **先现象后原理**：先让学生看到效果（curl 得到回复），再回头讲原理。

4. **词汇表上墙**：API、JSON、Mock、状态机、STT/LLM/TTS、固件、心跳——每学一个新词就贴一张卡。
5. **阶段二可压缩**：如果学生上手快，Python 基础可压到 6–8 课时，把时间留给阶段七、八的动手环节。

## 附录B：常见问题排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
